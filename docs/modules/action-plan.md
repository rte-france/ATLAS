# Run an Action Plan

An action plan runs a set of **tasks** on a recurring schedule — each task runs a module or a [workflow](workflow.md) repeatedly over its own time window, at its own frequency. Unlike a [workflow](workflow.md), which runs a fixed list of steps once, an action plan is built for rolling-horizon simulations: run `PortfolioOptimisation` every day for a month, or run a full day-ahead `Workflow` every week, each iteration processing the lastest output dataset generated by any task in the action plan.

---

## Define an Action Plan

An action plan is defined in a YAML file:

```yaml
name: monthly-portfolio
dataset_path: ./data/input/
output_dir: ./results/
tasks:
  - name: daily-portfolio
    module: PortfolioOptimisation
    parameters: ./parameters/portfolio_optimisation.yml
    from: '2028-01-01 00:00:00'
    until: '2028-01-31 00:00:00'
    frequency: 1d
    offset_start_date: 0m
    offset_end_date: 1d
```

As with a workflow, two different types of parameters are present in this YAML file:

- Top-level parameters either define global information (such as the action plan name), or are applied to *every* task.
- Task parameters define what a given task runs, and when.

### Top-level Parameters

| Parameter | Required | Default | Description |
|---|---|---|---|
| `name` | No | `null` | Name of the action plan |
| `dataset_path` | Yes | — | Path to the initial input dataset |
| `output_dir` | No | `.` | Root directory for per-task, per-iteration results |
| `path_from_action_plan` | No | `false` | Resolve relative paths from the action plan file location |
| `rollback_on_job_failure` | No | `true` | Roll back to the previous job's state if a job fails |
| `create_job_snapshots` | No | `false` | Save a dataset snapshot before each job |
| `export_output` | No | `true` | Export the output dataset after each job |
| `hooks` | No | `[]` | Reserved for future callback support — not yet implemented |

### Task Parameters

Every task, whichever type it runs, shares the same scheduling fields:

| Parameter | Required | Default | Description |
|---|---|---|---|
| `name` | No | module/workflow name | Custom name for the task |
| `from` | Yes | — | First execution date for this task |
| `until` | Yes | — | Last execution date for this task |
| `frequency` | No | `1m` | Interval between two consecutive executions |
| `offset_start_date` | No | `0m` | Offset from the execution date used as the run's `start_date` |
| `offset_end_date` | No | `0m` | Offset from the execution date used as the run's `end_date` |
| `priority` | No | `0` | Tie-breaker order when two tasks execute on the same date — lower runs first |

`frequency`, `offset_start_date`, and `offset_end_date` accept the same duration syntax as elsewhere in Atlas (e.g. `15m`, `1h`, `1d`, ISO 8601).

On top of these, exactly one of two task types must be chosen:

| Field | Task type | Description |
|---|---|---|
| `module` + `parameters` | `TaskModule` | Runs a single module (`DayAheadOrders`, `MarketClearing`, `PortfolioOptimisation`, `IntradayPriceForecast`) on each iteration. `parameters` can be a path to a parameters file or an inline mapping. |
| `workflow` | `TaskWorkflow` | Runs a [`Workflow`](workflow.md) on each iteration. `workflow` can be a path to a workflow YAML file or an inline mapping with the same shape as a workflow config. |

!!! note "Concurrent tasks"
    Two tasks that share the same `priority` and would, at some point, be scheduled to run on the same date cannot both belong to the same action plan — building it raises a `ValueError`. Give tasks that may land on the same date different priorities.

!!! note "Placeholder dates in module parameters"
    A `TaskModule`'s own parameters file still needs a `temporal` block with *some* `start_date`/`end_date`/`execution_date` to pass initial validation — Atlas overwrites all three with the task's real per-iteration dates before each run. Only `timestep` is kept from what you provide.

#### Inline Parameters

As with workflow steps, a task's module parameters — or an entire workflow — can be written directly in the action plan YAML instead of pointing to a separate file:

```yaml
name: monthly-portfolio
dataset_path: ./data/input/
output_dir: ./results/
tasks:
  - module: PortfolioOptimisation
    parameters:
      temporal:
        start_date: '2000-01-01 00:00:00'
        end_date: '2000-01-02 00:00:00'
        execution_date: '2000-01-01 00:00:00'
    from: '2028-01-01 00:00:00'
    until: '2028-01-31 00:00:00'
    frequency: 1d
```

## Run

### CLI

```bash
atlas action-plan run action_plan.yaml
```

To inspect the tasks of an action plan file before running it:

```bash
atlas action-plan list action_plan.yaml
```

### Python

```python
from atlas.orchestrator.actionplan.action_plan import ActionPlan

action_plan = ActionPlan.from_file("action_plan.yaml")
action_plan.execute()
```

Unlike `Workflow`, `ActionPlan` is not re-exported at the top level of the package — import it from `atlas.orchestrator.actionplan.action_plan`.

### Programmatic

You can also build an action plan directly in Python, without a YAML file:

```python
from atlas.orchestrator.actionplan.action_plan import ActionPlan
from atlas.orchestrator.actionplan.parameters import ActionPlanParameters, TaskModule, TaskWorkflow
from atlas import Workflow, WorkflowParameters
from atlas.orchestrator.workflow.parameters import Step

workflow = Workflow(WorkflowParameters(
    dataset_path="./data/input/",
    steps=[Step(module="DayAheadOrders", parameters_path="./parameters/day_ahead_orders.yml")],
))

parameters = ActionPlanParameters(
    name="monthly-portfolio",
    dataset_path="./data/input/",
    output_dir="./results/",
    tasks=[
        TaskModule(
            name="daily-portfolio",
            module="PortfolioOptimisation",
            parameters="./parameters/portfolio_optimisation.yml",
            from_="2028-01-01 00:00:00",
            until="2028-01-31 00:00:00",
            frequency="1d",
        ),
        TaskWorkflow(
            name="weekly-day-ahead",
            workflow=workflow,
            priority=1,
            from_="2028-01-01 00:00:00",
            until="2028-01-31 00:00:00",
            frequency="7d",
        ),
    ],
)

action_plan = ActionPlan(parameters=parameters)
action_plan.execute()
```

Note the trailing underscore: `from_` is a Python keyword, so the field is `from_` in code (the YAML key remains `from`).

This is useful for building action plans dynamically, for example when the schedule depends on runtime conditions.

## Accessing Results

After execution, access the final output dataset the same way as a workflow:

```python
action_plan.execute()

# Final dataset after the last job in the schedule
result = action_plan.get_output_dataset()

for order in result.order.all():
    print(f"{order.name}: {order.accepted_power} MW")
```

## Directory Layout

A typical action plan project:

```
my-action-plan/
├── action_plan.yaml
├── data/
│   ├── input/                          # Initial dataset (dataset_path)
│   └── output/                         # Final dataset
├── parameters/
│   └── portfolio_optimisation.yml
└── results/                            # Per-task, per-iteration outputs (output_dir)
    └── daily-portfolio/
        ├── 2028-01-01T00:00:00+00:00/
        ├── 2028-01-02T00:00:00+00:00/
        └── ...
```

Each task gets its own sub-directory named after the task, and each iteration within it gets its own sub-directory named after that iteration's execution date. A `TaskWorkflow` follows the same `<output_dir>/<task_name>/<execution_date>/` pattern, with the workflow's own step outputs further inside.

When `path_from_action_plan: true`, all relative paths in `action_plan.yaml` are resolved from the directory containing the action plan file — so you can move the whole folder without breaking paths.

## Advanced Options

### Rollback on Failure

With `rollback_on_job_failure: true` (default), if a job fails the dataset is restored to its state before that job. This prevents a partial run from leaving the dataset in an inconsistent state.

```yaml
rollback_on_job_failure: true  # safe default — always restore on failure
```

Set to `false` only if you want to inspect the dataset state at the point of failure.

### Job Snapshots

With `create_job_snapshots: true`, Atlas saves a copy of the dataset before each job. Useful for debugging — you can reload from any snapshot and re-run from that point.

```yaml
create_job_snapshots: true
```

Snapshots are named after the job, e.g. `input_task <name> iteration <n>`.

### Scheduling & Priority

The scheduler interleaves every task's iterations into a single ordered stream of jobs, sorted first by execution date, then by `priority` for iterations that land on the same date:

```yaml
tasks:
  - name: fast-check
    priority: 0    # runs first on shared dates
    frequency: 1d
    ...
  - name: full-run
    priority: 1    # runs second on shared dates
    frequency: 7d
    ...
```

Two tasks sharing a `priority` may never actually land on the same date — see the note on [concurrent tasks](#task-parameters) above.
